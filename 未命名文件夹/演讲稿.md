## 1. 开场（30 秒）

【共享屏幕，停在代码编辑器或已打开的程序界面】

老师好，各位同学好。我是 XXX。我今天分享的产品是**出纳管理之银行对账系统**——它解决一个很实际的问题：企业月底对账时，日记账几十笔、对账单几十笔，会计要人工一笔笔找、一笔笔画勾，费时还容易错。我的系统把这些流水导进来，**3 秒钟自动核对完，并直接生成交给老师看的《银行存款余额调节表》**。

整个产品对应学习通 3.5.5 节点，是一条完整的成果链：Python 核心代码、AI 协作开发的图形界面、pyinstaller 打包的 exe、以及已推送到 gitee 的开源仓库。下面按这条链来讲。

## 2. 产品设计（2 分钟）

【切到 README.md 的"成果链总览"表格，或对着文件列表讲】

先讲设计思路，两个字：**分层**。

我把项目拆成两个核心文件：

- `bank_core.py`——**算法层**。对账匹配、未达账四分类、余额滚动、调节表计算，全在这里，它一个界面库都不引用，是纯函数；
- `银行对账系统.py`——**界面层**。Tkinter 写的桌面 GUI，只做一件事：收数据、调算法、展示结果。

这样拆有三个好处：第一，算法可以**脱离界面做单元测试**——我写了 18 个测试用例全部通过；第二，以后想换成 Web 界面，算法一行不用改；第三，改界面不会不小心弄坏对账逻辑。这是我在 AI 协作开发里学到最重要的工程思想：**让 AI 帮我写代码之前，先让架构替我把职责划清楚**。

业务口径完全对齐教材：对账输入是企业日记账和银行对账单的流水，每条五个字段——日期、结算方式、票号、借方金额、贷方金额；输出是已达账、四类未达账，和交叉调节口径的期末余额调节表。**期初未达账自动结转**——上月的银行已收企业未收，这个月会出现在本月对账单里，系统自动配对核销，不会重复挂账。

## 3. 核心算法（2 分钟）

【切到 bank_core.py 的 run_reconciliation 函数，滚动到三轮匹配处】

对账的灵魂就一个问题：**两笔流水怎么算"是同一笔业务"**？

我做成了**三轮匹配**：

- **第一轮，严格匹配**：结算方式 + 票号 + 借方金额 + 贷方金额，**四字段全等**——这和学习通 3.5.5 的判定口径完全一致，结果最可信；
- **第二轮，容错匹配**：票号 + 金额 + 同方向。解决什么？实际录入时两边日期写法经常不一样，比如企业记 12.1、银行记 12 月 1 日，严格口径就配不上了，票号金额对得上就先兜住；
- **第三轮，容错匹配**：日期 + 金额 + 同方向，给没票号的流水兜底。

容错匹配的配对，界面上用 **问号加淡黄底色** 标出来，提醒会计人工复核——**程序辅助对账，但最终决定权交给人**，这是财务软件的底线。

再说两个容易翻车的细节：一是**金额精度**，0.1 加 0.2 在计算机里不等于 0.3，所以金额比较我留了半分钱容差；二是**性能**，严格匹配我用字典索引实现，复杂度 O(n)，几千笔流水也是秒级。

 correctness 我不空口说：用教材表 3-14/15/16 的示例账套跑，标准答案是 **22 对已达、双方各 4 笔未达，两端调整后余额 448,067.78 元、完全平衡**——这组数字就写在我的单元测试断言里，每次改完代码跑一遍，绿了才算数。

## 4. 图形界面演示（3 分钟）

【现在切到正在运行的程序。提前把窗口最大化，字体调好】

**第一步，载入数据。** 点【载入示例数据】——程序自动完成期初结转、对账、生成调节表。【指着流水清单】大家看，每笔流水都有了滚动余额，最后一笔 741,709.78，和日记账账面期末一致。

**第二步，看对账结果。** 【指着"已达"列】√ 是严格匹配的 22 对；【切到下方未达账面板】未匹配的自动分成四类——企业方 4 笔：Z1003、Z1015 是企业已收银行未收，Z2002、Z1010 是企业已付银行未付；银行方 4 笔，同理。注意 Z1010 两边票号相同但金额一个 98520 一个 178000，这就是教材里那笔**记账金额差错**，系统没有强行配对，而是诚实地两边都挂未达——宁可报异常，不替账掩盖问题。

**第三步，看调节表。** 【指着右侧】企业账面 741,709.78，加银行已收 242,808、减银行已付 536,450，调整后 448,067.78；银行侧同样算出来也是 448,067.78——**两端相等，对账平衡**，绿字提示。这一张表就可以直接交给老师。

**第四步，导出交付。** 点【导出 Excel】，生成 6 个 Sheet：期初调节表、日记账、对账单、期末调节表、已达明细、未达明细，格式对齐教材模板。

**第五步，存档续作。** 这是我 v2 新加的：点【保存项目】，全部数据存成一个 JSON 文件；【关掉程序再打开】点【打开项目】，数据原样恢复——**关掉软件不丢账**，打包给客户后他可以分几天做账。

（如果时间富余）最后演示一下双击任意流水行，可以直接修改，改完系统提示重新对账——所有结果都是可追溯、可修正的。

## 5. exe 打包与 git 开源（1 分 30 秒）

【切到终端或 README 打包一节；如果已配好 GitHub Actions，切到 Actions 绿色对勾页面最有说服力】

打包用 **pyinstaller**，核心就一条命令：

```
pyinstaller -F -w --add-data "示例数据.csv;." 银行对账系统.py
```

`-F` 打成单个 exe，微信就能发；`-w` 去掉黑窗口；`--add-data` 把示例数据打进包里。**Windows 客户双击就能用，不需要安装 Python**。代码里我做了 `sys._MEIPASS` 兼容，单文件模式下照样能找到数据文件。

我的开发机是 Mac，而 pyinstaller 不能跨平台打 exe，所以我用了开源项目的标准做法——**CI/CD 云端打包**：仓库里配了一个 GitHub Actions 工作流，每次 push 代码，GitHub 自动在它的 **Windows 虚拟机**里执行这条打包命令，几分钟后 exe 就能在 Actions 页面下载。【指屏幕上的绿色对勾和 Artifact】整个流程没有人肉环节，代码更新 exe 就自动跟着更新。

开源走 git + gitee：本地 `git init`、`git add`、`git commit`，gitee 建好空仓库后 `git remote add origin` 加上 `git push -u origin master`，源码就开源上去了（我同时推了 GitHub 跑自动打包）。仓库里的 `.gitignore` 排除了打包产物和我的个人账目数据——**开源的是代码，不是我的账**。

## 6. 对老师学习通产品的不足与改善建议（1 分钟）

【语气：先肯定，再提建议】

老师在 3.5.5 的参考小产品帮我把口径打牢了，认真研究之后，我提三点可以更好的地方：

**第一，数据没有持久化。** 全部数据在内存里，窗口一关就没了。exe 交付给客户后，客户录了一下午账，误关软件就全丢了。我的做法是加"保存项目 / 打开项目"，一个 JSON 文件解决。

**第二，匹配口径单一、缺少人工干预通道。** 四字段全等很严谨，但结算方式一边写"202"一边写"电汇"、或者票号大小写不同，就整笔落成未达账；而且日期不参与严格匹配，跨期重复票号有错配风险。我加了两轮容错加问号标记，先兜住再让人复核，兼顾严谨和实用。

**第三，导入环节自动猜工作表，猜错了用户不知道。** 我建议识别完弹出确认框让用户点一下头，交互会踏实很多。

这三点我都在自己的 v2 里做了对应实现，欢迎老师检验。
